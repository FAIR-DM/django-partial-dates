# Research — FS-007: Ready-made django-filter filters and a Django REST framework field

Read against django-filter 26.2 and Django REST framework 3.18.3 as installed in this repository's
environment, and run against a prototype of the design below on Django 6.1.

## What the libraries do with the field

- `FilterSet.filter_for_lookup` (`django_filters/filterset.py`) reads `Meta.filter_overrides` for the
  field's class, and raises nothing but `AssertionError` from `handle_unrecognized_field` when there
  is no mapping. `resolve_field` follows a transform to its output field first, so `year`, `month`
  and `day` become `NumberFilter` and `isnull` becomes `BooleanFilter` whatever the mapping says.
- For `in` and `range`, `filter_for_lookup` subclasses the mapped filter with `BaseInFilter` or
  `BaseRangeFilter`, which swaps the form field for a comma-separated one. With the prototype that
  was silently wrong: `c__in=1990` validated and found nothing. So the filter refuses these lookups
  when it is built, which is when `Meta.fields` is read. The spec leaves `range` and `in` out of
  `Meta.fields`, and a clear refusal is the smallest way to keep that promise.
- `Filter.field` builds `field_class(label=..., **extra)`, so a keyword argument of the filter
  reaches the form field. That is how `years` travels.
- `RangeFilter.filter` turns a `slice` into one `.filter()` call, `range` with both ends and `gte`
  or `lte` with one. One call means one join, so FR-006 holds with nothing added. Passing it a
  `slice` whose stop is the last day of the period gives D3 with almost no code.
- `SuffixedMultiWidget` renames only its direct subwidgets after they are built, so nested selects
  would keep `_0` and `_1` in their names. Django's own `MultiWidget` with a dict of widgets names
  them `_after` and `_before` all the way down, and needs no django-filter class.
- `DjangoFilterBackend.raise_exception` is true, so an invalid filter set becomes a 400 response.
- `FilterSet.qs` drops an invalid filter from `cleaned_data` and filters on the rest. `FilterView`'s
  `strict` decides what a page shows then. Neither reaches the database with a refused entry.
- `MultiValueField.clean` raises `invalid` for anything but a list or tuple, so a filter's field
  takes the text before calling it.
- `PartialDateWidget.decompress` gives three `None`s for text that is not an ISO form, and
  `get_context` already handles text as a value, so a page opened on an ISO address shows its parts.
- `PartialDate.end` is a `datetime.date`, which a lookup refuses by design, so the last day of the
  period is made into a day-precision `PartialDate`.
- `serializers.Field` needs only `to_representation` and `to_internal_value`. `Field.get_value`
  handles HTML input and `validate_empty_values` handles `null`, `required` and `read_only`, so the
  field has neither. `Field.fail` formats its message with `str.format`, so it holds no braces.

## Choices

- **Lowest versions:** `django-filter>=26.2` and `djangorestframework>=3.18`. These are what the
  tests run, and their metadata names Django 5.2, 6.0 and 6.1, every version the package supports.
- **The dev group** carries both, as it carries django-reversion, so the shared test workflow gets
  them with no change to `.github/`.
- **No `INSTALLED_APPS` entry** is needed for either library by anything in the package: it uses no
  template or static file of theirs.
